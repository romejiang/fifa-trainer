# FIFA / EA FC 花式动作练习器（Windows / macOS）

连上手柄就能练花式动作：**250Hz** 实时识别右摇杆轨迹，做对了手柄震一下；
没做对也会当场告诉你**是快了、慢了，还是起点 / 终点 / 保持时间不对**。

- **桌面窗口**：每个动作本次运行的累计成功数、10 个一组进度、最近一次结果、双摇杆同图可视化
- **命令行**：挂在后台只报动作名，不打扰你打游戏
- 可打包成 Windows `.exe` / macOS `.app`，双击即用

针对 **飞智八爪鱼 4（Flydigi Vader 4 / Apex 4）** 实测通过。
手柄走 SDL / pygame-ce，XInput、DInput、蓝牙都支持。

---

## 一、安装

需要 Python 3.11+ 和 [uv](https://docs.astral.sh/uv/)。Windows 和 macOS 步骤一样：

```powershell
cd C:\Users\romej\Documents\fifa19-script   # 换成本机上的项目目录
uv sync
```

```bash
cd ~/Documents/fifa19-script                 # macOS 示例
uv sync
```

首次运行 `uv` 会自动下载 Python 与 pygame-ce，运行时不需要手动激活虚拟环境。

> **macOS 首次连接手柄**：到「系统设置 → 隐私与安全性 → 输入监控」里，
> 把终端（或打包后的 App）勾上，否则读不到摇杆。改完权限需要重启程序。

如果想从零复现同样的环境：

```bash
uv init --name fifa-skill-rumble --python 3.11 --bare .
uv add pygame-ce
```

## 二、跑起来（桌面窗口 / 命令行）

### 桌面窗口（推荐）

```bash
uv run app.py          # 也可以 uv run main.py --gui
```

没有手柄也想先看看界面（会循环播放成功和失败的轨迹）：

```bash
uv run app.py --demo
```

窗口里能看到：

- **左栏**：每个动作的 10 个一组进度（右上角 `3/10`），以及**本次运行累计成功数**
  （`成功 37`，按 `R` 清零）；最近一次的结果
- **中间**：最近一次做成了没有、失败原因、耗时，以及该怎么改
- **尝试记录**：保留最近 **50 条**，每行除了动作名和毫秒数，成功时还会写出
  实际旋转角度、经过的角度范围、保持时长等调参数据（例如
  `旋转 101°（相对 180°→281°）`、`相对朝向 右/左 90°~94°（平均 92°） 保持 352ms`）
- **底部**：**一个圆环同时显示两个摇杆**——红色指针 + 红球是左摇杆（球员朝向），
  蓝色指针 + 蓝球是右摇杆；两条指针都从圆心指向当前方向，推到底时球的外缘
  都贴住圆环。红色线条/球比蓝色粗 2px，两个方向重合时也能看见红色边缘。
  旁边直接写出
  `右摇杆 相对 92°`（**相对球员朝向**，不是屏幕绝对角度），一眼就能看出
  两个方向差了多少度。球员朝向只显示方向名（如 `球员朝向 右`），不显示绝对度数。
  左摇杆回中时红针消失并显示 `左摇杆回中 / 方向类动作暂不可用`。

尝试记录可以用**鼠标滚轮**滚动，也可以按 `PageUp` / `PageDown` / `Home` / `End`。
快捷键：`R` 清零统计和记录，`C` 打开配置文件所在文件夹，`Esc` 退出。
没连手柄时窗口会一直等着，插上会自动重试，也可以按 `R` 立即重试。

### 命令行

切到 FIFA 窗口之前，建议按这个顺序走一遍，出了问题好定位：

```powershell
# 1. 确认手柄被识别到，看设备名 / 轴数 / 是否有 SDL 映射表 / 震动接口是否可用
uv run main.py --list

# 2. 校准：实时显示左右摇杆的角度与幅度、按下的按键（名称 + 原始编号）
#    把两个摇杆各推一圈、每个键按一遍，核对显示对不对
uv run main.py --debug

# 3. 想看识别器的内部进度（比如"旋转中 120°，目标 70~230°"），加 --trace
uv run main.py --debug --trace

# 4. 震动自检 + 震感对比：依次试每个后端，再用不同强度/时长各震一下
uv run main.py --selftest

# 5. 正式运行（切到 FIFA 窗口）。默认只报识别到的动作，一次一行
uv run main.py

# 想看每次触发的角度轨迹等细节，加 --verbose
uv run main.py --verbose

# 想知道每次失败是为什么，加 --feedback
uv run main.py --feedback
```

常用参数：

| 参数 | 作用 |
|---|---|
| `--gui` | 打开桌面练习窗口（等同 `uv run app.py`） |
| `--demo` | 窗口演示模式：不用手柄，循环播放成功/失败轨迹 |
| `-v` / `--verbose` | 输出完整信息：键位映射、动作参数表、每次触发的轨迹详情 |
| `--debug` | 单行实时刷新摇杆角度/幅度/按键编号，校准用 |
| `--trace` | 在 `--debug` 基础上多一行显示各动作识别器的实时进度 |
| `--list` | 列出手柄设备 |
| `--selftest` | 震动自检 + 震感对比 |
| `--feedback` | 除了成功，也打印每次失败的原因 |
| `--no-rumble` | 本次不震动（只打印触发日志，方便先验证识别准不准） |
| `--index N` | 选择第 N 个手柄 |
| `--duration 5` | 只跑 5 秒后自动退出并打印统计 |
| `-c 路径` | 指定别的配置文件 |
| `--write-config` | 重新生成一份默认 `skills_config.json` |

### 做错了会告诉你为什么

**失败不震动**——震动只代表"做对了"。失败会显示在窗口里（命令行加 `--feedback` 才打印）：

```
[21:34:21] ✗ 踩单车 — 转得不够：只转了 97°（需要 70°~135°）
```

完整的原因列表：

| 原因 | 显示示例 | 通常是哪里出了问题 |
|---|---|---|
| 太快 | `太快了：56ms 就转到位了（至少 100ms）` | 一甩而过，动作没做完整 |
| 太慢 | `太慢了：用了 900ms（上限 550ms）` | 中途犹豫，整体拖太久 |
| 转得不够 | `转得不够：只转了 60°（需要 70°~230°）` | 弧没画满就松手了 |
| 转多了 | `转多了：累计 260°（上限 230°）` | 到点没收住，多带了一段 |
| 起点不对 | `起点不对：从 90° 起手（要求 180°±65°）` | 起手方向错了 |
| 终点不对 | `终点不对：停在 90°（应该回到 0°±80°）` | 收尾方向错了 |
| 方向反了 | `转向反了：应该逆时针` | 转反了 |
| 中途停住 | `中途停住了：超过 250ms 没转动` | 画弧过程中停手了 |
| 没做完 | `没做完：只做到第 1/2 步（前 → 还差 后）` | 序列动作只做了一半 |
| 保持不够 | `保持不够：只保持了 280ms（需要 350ms）` | 需要按住的动作松手太早 |

一次手势只会给一条裁定：如果它已经被某个动作成功认领，别的动作不会再来插嘴报"没做完"。

```

手柄 Xbox One S Controller  |  震动 pygame-ce Joystick.rumble()

Ctrl+C 退出。

[21:34:07] ✓ 马赛回旋 Roulette
[21:34:12] ✓ 踩单车 Stepover
[21:34:15] ✓ 磕球过人 Heel-to-Heel

```

### 界面里的尝试记录（调参用）

窗口里的"最近的尝试"会保留最近 50 条，**每条占一行**：左边是动作
（时间 / ✓✗ / 名称），右边是详情（毫秒数 + 实测数据或失败原因）。
成功详情用灰色，失败详情用红色，一屏显示 5 条，其余用滚轮翻看。
成功行在毫秒数后面附上这次动作的实测数据，方便对照 `skills_config.json` 慢慢调：

```
✓ 马赛回旋 Roulette 412 ms    旋转 101°（相对 180°→281°）
✓ 油炸丸子 La Croqueta 356 ms  相对朝向 右/左 90°~94°（平均 92°） 保持 352ms
✓ 磕球过人 Heel-to-Heel 431 ms  相对朝向 前 6° · 后 186°
✗ 踩单车 Stepover 180 ms       太快了：整个动作只用了 180ms（至少 250ms）
```

> 日志和界面里的所有角度都是**相对球员朝向**的：`0°` = 正前方、`90°` = 右侧、
> `180°` = 正后方、`270°` = 左侧。不需要自己再拿右摇杆的绝对角度去减朝向。

- **旋转类**：`旋转 X°` 是真正触发那一刻累计转过的角度，括号里是起点→终点。
- **方向类**（油炸丸子/磕球）：每一步都会给角度；样本角度差小于 3° 时只显示平均值，
  否则显示范围 + 平均值。
- **保持类**：`保持 Xms` 是推过 `enter_threshold` 后、触发时的实际保持时长。
- 同样的内容也会写进 `trainer.log` 的 `结果 ✓/✗ ...` 行。

加上 `--feedback` 才会多打印失败行（失败不震动）：

```
[21:34:21] ✗ 踩单车 — 转得不够：只转了 97°（需要 70°~135°）
```

退出时给一个简短统计（成功 / 尝试 + 成功率 + 最常犯的错）：

```
──────────────────────────────────────────────
运行 47s | 250Hz | 共触发 43 次
    13/19   马赛回旋 Roulette        68%   最多: 太快 ×3
    10/12   磕球过人 Heel-to-Heel    83%
    20/24   油炸丸子 La Croqueta     83%   最多: 保持不够 ×2
     8/10   绿色搓射 Green Finesse  80%
  未尝试: 踩单车 Stepover
──────────────────────────────────────────────
```

采样调度落后、震动后端报错这类异常只在**真的发生**时才会多出一行。

想看完整细节（每次触发的角度轨迹、按键映射、动作参数表）就加 `--verbose`。

> 觉得动作名太长可以自己在 `skills_config.json` 里把 `name` 改短，日志用的就是这个字段。

## 三、角度约定（配置里写方向时看这里）

```
        0°  前 / forward / up
        ↑
270° ←--+--→ 90°   左 / left          右 / right
        ↓
      180°  后 / back / down
```

**角度增大 = 屏幕上的顺时针方向。**

`relative_to_ls: true` 时，0° 表示**球员正前方**（由左摇杆方向决定），
90° 是球员右侧，180° 是正后方。**左摇杆回中就没有朝向**：方向类动作不成立，
窗口底部会显示"回中"并提示暂时不可用；推着左摇杆才有判定基准。

## 四、内置的五个示例动作

| 动作 | 类型 | 搓招方式 |
|---|---|---|
| 马赛回旋 Roulette | `arc` | 从**身后**（相对左摇杆 180°）起，右摇杆往身前转（累计 70°~230°；和踩单车一样，底线都是 70°） |
| 踩单车 Stepover | `arc` | 从**身前**（相对左摇杆 0°）起，右摇杆转向**侧面**（累计 70°~135°） |
| 磕球过人 Heel-to-Heel | `sequence` | 右摇杆向前点拨一下 → 回中 → 向后点拨一下 |
| 油炸丸子 La Croqueta | `sequence` | 按住 L1，右摇杆**相对左摇杆朝向**偏左或偏右 **90°**（正侧向，容错 80°~100°），保持约半秒（阈值 350ms） |
| 绿色搓射 Green Finesse | `taps` | 按住 **RB**（或 **RT**）不松，按一下 **X**，**400~600ms** 后再按一下 **X**；与右摇杆、球员朝向无关 |

**所有动作统一震动：低频大马达 0.8、120ms，一次动作只震一下。**

### 判定规则（几个动作共用）

- **起点 + 终点都要对。** 马赛回旋和踩单车的差别就在**起点**：从后往前转是马赛回旋，
  从前往侧转是踩单车。只看"转了多少度"是不够的，那样两者会互相误判。
  光看起点也不够——转到一半停下来的不算，所以还要看**终点**方向（`end_angle`）。
- **每个动作都有时间窗口。** 内置动作统一要求 **250~600ms** 完成（`min_duration_ms` /
  `max_duration_ms`）：比 250ms 快的手势在 FIFA 里根本搓不出来，所以直接**作废**，
  而不是"等够时间再补触发"；超过 600ms 也算没做成。
- **中途停顿超过 `idle_timeout_ms` 就作废。** 这是为了不让"上一个动作的尾巴"
  被当成"下一个动作的开头"——中间停了一两秒，两段就是两段。
- **一次动作只认一个技能。** 触发之后引擎会锁住识别，直到右摇杆真正回中并保持
  `gesture_release_ms`（默认 150ms）。所以按住不放只会震一次，不会连着震。
- **按住修饰键时只判定对应的动作。** 现在按住 L1 就只判定油炸丸子，其他动作整段跳过；
  它们的半截进度会被静默丢弃，不会在旁边误报"没做完"。按住 RB 或 RT 时同理，只判定绿色搓射。
- **按键类动作不看右摇杆和球员朝向。** 绿色搓射只要求修饰键（RB 或 RT）全程按住、
  两下 X 的间隔在 400~600ms 内；左摇杆回中也能做。

> La Croqueta 用的是"保持"而不是"点拨"——只推一下不算数，由步骤里的 `hold_ms` 实现。
> 而且**按住不放只会震一次**：必须真正松开摇杆，才允许做下一次。
>
> 两个容易踩的坑：
> 1. **方向是相对左摇杆（球员朝向）判定的**：右摇杆要偏在左摇杆方向的正左 90°
>    或正右 90°（即相对角 270° / 90°），左右都算。判定窗口是 80°~100°
>    （`tolerance_deg: 10`）。跑动方向一转，目标方向也跟着转，
>    所以不能写成屏幕绝对方向，否则往侧边跑时永远对不上。
>    左摇杆回中时没有朝向，这一步不会成立。
> 2. **`hold_ms` 从右摇杆推过 `enter_threshold`（60%）那一刻开始计时。**
>    真手推杆还有几十毫秒行程，所以"推住半秒"实际只记到 450ms 左右；
>    门槛取 350ms 是给这段行程留余量。

## 五、怎么加自己的动作

**只需要改 `skills_config.json`，不用动 Python 代码。** 改完存盘，重新 `uv run main.py` 就生效。

### 例 1：画弧类动作模板（以踩单车为例）

内置动作已经包含踩单车；新增自己的画弧动作时，可以复制下面这段并改成不重复的名字：

```json
{
  "name": "我的踩单车 My Stepover",
  "enabled": true,
  "type": "arc",
  "relative_to_ls": true,
  "required_button": null,
  "params": {
    "start_angle": 0,
    "start_tolerance": 55,
    "end_angle": [90, 270],
    "end_tolerance": 55,
    "enter_threshold": 0.72,
    "exit_threshold": 0.52,
    "min_angle": 70,
    "max_angle": 135,
    "min_duration_ms": 250,
    "max_duration_ms": 600,
    "idle_timeout_ms": 250,
    "release_hold_ms": 120,
    "direction": "any"
  },
  "rumble": { "low": 0.8, "high": 0.0, "duration_ms": 120 },
  "cooldown_ms": 350
}
```

### 例 2：加一个"麦吉迪转身"（按住 L1 + 右摇杆从前往侧面转 90°）

```json
{
  "name": "麦吉迪转身 McGeady Spin",
  "enabled": true,
  "type": "sequence",
  "relative_to_ls": true,
  "required_button": "L1",
  "params": {
    "steps": ["forward", ["left", "right"]],
    "tolerance_deg": 35,
    "enter_threshold": 0.65,
    "release_threshold": 0.35,
    "min_duration_ms": 250,
    "max_duration_ms": 600,
    "idle_timeout_ms": 250,
    "release_hold_ms": 150,
    "require_neutral_between_steps": true
  },
  "rumble": { "low": 0.8, "high": 0.0, "duration_ms": 120 },
  "cooldown_ms": 450
}
```

### 例 3：需要"按住"而不是"点拨"的动作（比如 La Croqueta）

把步骤写成对象，加 `hold_ms`，表示方向对了之后还要**连续保持**这么久才算数：

```json
{
  "name": "油炸丸子 La Croqueta",
  "enabled": true,
  "type": "sequence",
  "relative_to_ls": true,
  "required_button": "L1",
  "params": {
    "steps": [
      { "direction": ["右", "左"], "hold_ms": 350 }
    ],
    "tolerance_deg": 10,
    "enter_threshold": 0.6,
    "release_threshold": 0.3,
    "min_duration_ms": 250,
    "max_duration_ms": 600,
    "idle_timeout_ms": 350,
    "release_hold_ms": 150,
    "require_neutral_between_steps": true
  },
  "rumble": { "low": 0.8, "high": 0.0, "duration_ms": 120 },
  "cooldown_ms": 450
}
```

`max_duration_ms` **必须大于**所有步骤 `hold_ms` 之和，否则这个动作永远触发不了
（配置文件校验会直接拦下来并告诉你）。同理 `max_duration_ms` 也必须大于
`min_duration_ms`。

`hold_ms` 也可以用在多步序列的任意一步上，比如"先点拨一下前方，再按住侧向 400ms"：

```json
"steps": ["forward", { "direction": "left", "hold_ms": 400 }]
```

### 例 4：按键双击类动作（绿色搓射）

不碰右摇杆，只看按键：按住 `required_button`，在时间窗口内按两下 `button`。
下面这段就是内置绿色搓射：默认按住 RB，两下 X 的间隔必须在 400~600ms；
在界面里点一下卡片上的 **RT**，就会改成按住 RT 判定，并写回配置文件。

```json
{
  "name": "绿色搓射 Green Finesse",
  "enabled": true,
  "type": "taps",
  "relative_to_ls": false,
  "required_button": "RB",
  "params": {
    "button": "X",
    "min_interval_ms": 400,
    "max_interval_ms": 600,
    "timeout_grace_ms": 150,
    "release_hold_ms": 120,
    "modifier_options": ["RB", "RT"]
  },
  "rumble": { "low": 0.8, "high": 0.0, "duration_ms": 120 },
  "cooldown_ms": 450
}
```

- `required_button` 必须全程按住；中途松开会在日志里报 `保持不够`。
- `modifier_options` 给界面提供可点击的备选键（这里是 RB / RT），默认选中
  `required_button` 写的那一个。点击后立即切换判定，并把选中的键写回配置文件；
  射门键始终是 `button`（X），不会跟着变。
- `min_interval_ms` / `max_interval_ms` 只计算**两次按下沿**之间的时间。
- `timeout_grace_ms`：超过上限后再等这么久仍没有第二下，就报 `太慢`。
- 这类动作与右摇杆、球员朝向完全无关，左摇杆回中也能判定。

### 震动参数

五个内置动作统一使用一组简单的震动参数，新增动作也建议直接沿用：

```json
"rumble": { "low": 0.8, "high": 0.0, "duration_ms": 120 }
```

`low` 是低频大马达，`high` 是高频小马达。当前默认关闭高频马达，
每次识别成功只震一次，避免不同动作的手感不一致。

**震动引擎一次只播一个脉冲，不排队。** 写多个脉冲（`"pattern": [...]`）也只会播第一个。
以前是会把多次触发排成队列背靠背播放的，结果就是"有时候震得特别长、甚至一直在震"——
几次触发被串成了一串。现在一次触发 = 一次固定时长的震动，到点一定停；
上一次还没结束就来的新触发直接丢掉（正常搓招不会撞上，识别端有手势锁 + 冷却兜着）。

### 震感怎么调才感觉得到

这是实测踩过的坑，两条经验：

- **`duration_ms` 不要低于 80。** 震动马达需要 20~40ms 才能转起来，低于 80ms 的脉冲
  大半时间都花在启动和停止上，几乎感觉不到。默认的 120ms 比较稳妥。
- **一定要给 `low` 一个非零值。** 只写 `high` 的话大马达完全不工作，震感会非常微弱。
  默认 `low` 为 0.8；如果还是太弱，可以调到 1.0，不建议缩短时长。

拿不准就跑 `uv run main.py --selftest`，它会依次用不同强度/时长各震一下，
让你直接挑出自己感觉得到的组合。

## 六、字段速查

### 通用字段

| 字段 | 说明 |
|---|---|
| `name` | 动作名，随便起（**必须唯一**，日志用它区分） |
| `enabled` | `true` / `false` |
| `type` | `"arc"` 画弧类 / `"sequence"` 方向点拨类 / `"taps"` 按键双击类 |
| `relative_to_ls` | `true` = 以左摇杆朝向为正前方；`false` = 屏幕绝对方向 |
| `required_button` | 修饰键，如 `"L1"`；不需要写 `null`。也可以写数组 `["L1","R1"]` |
| `button_mode` | `required_button` 是数组时：`"all"` 全按 / `"any"` 任一 |
| `cooldown_ms` | 触发后的冷却，防止同一次搓招连震 |

按键名可以用 **`L1/R1/L2/R2/L3/R3`**（PlayStation 叫法）或 **`LB/RB/LT/RT/LS/RS`**（Xbox 叫法），两者等价。

### `input` 里跟识别节奏有关的两个参数

| 字段 | 说明 |
|---|---|
| `idle_reset_ms` | 右摇杆归中并静止这么久（默认 250），就清空**所有**动作的未完成进度。这是防止"上一个动作的尾巴接成下一个动作的开头"的总闸。 |
| `gesture_release_ms` | 一次触发之后，右摇杆要归中并保持这么久（默认 150）才解锁识别。所以按住不放只会震一次。 |

这两个是**全局**的，改这里会影响所有动作；每个动作自己的 `idle_timeout_ms` /
`release_hold_ms` 则是针对该动作的、更细的一层。

### 摇杆方向反了怎么办

偶发情况：手柄报上来的轴方向和物理方向相反（比如右摇杆上推，程序却认为是"后"）。
不用重写整套 `axis_layout`，在 `input` 里单独翻转那一根轴就行：

```json
"input": {
  "invert": { "rs_y": true }
}
```

可选键：`ls_x` / `ls_y` / `rs_x` / `rs_y`。写 `false` 表示强制不反转
（可以盖过 SDL 映射表自带的 `~` 标记）。

怎么判断该改哪个：跑 `uv run main.py --debug`，**右摇杆向上推**，
读数应该是 `RS   0.0°`（正前方）；如果显示 `180.0°`，就是 `rs_y` 反了。
左右反了同理（右推应是 `90.0°`）。窗口右下角的圆点也应该跟着拇指走。

### `type: "arc"` 的参数

| 参数 | 说明 |
|---|---|
| `start_angle` | **画弧的起点**必须是哪个方向（可写方向名或角度），`null` = 不限制 |
| `start_tolerance` | 起点容错夹角，默认 60 |
| `end_angle` | **画弧的终点**方向，可写一个方向或数组（如 `[90, 270]`），`null` = 不限制 |
| `end_tolerance` | 终点容错夹角，默认 60 |
| `enter_threshold` | 摇杆推过这个幅度才开始计弧（0~1，建议 0.72） |
| `exit_threshold` | 掉到这个幅度以下算结束（要比 `enter` 小，做迟滞） |
| `min_angle` / `max_angle` | 累计旋转角度的合格区间（度）；**转超过 `max_angle` 直接作废**，不靠回退蒙混 |
| `min_duration_ms` | 至少要花这么久，**太快直接作废**（默认 250） |
| `max_duration_ms` | 必须在这个时间内完成（默认 600） |
| `idle_timeout_ms` | 停在原地不转超过这么久就作废（默认 180） |
| `release_hold_ms` | 触发/作废后要连续回中这么久才允许下一段（默认 120） |
| `direction` | `"any"` / `"cw"` 只认顺时针 / `"ccw"` 只认逆时针 |

> `start_angle` 是区分动作的关键。比如"从后往前转 180°"是马赛回旋、
> "从前往侧转 90°"是踩单车——两者转的角度可能一样，只有起点不同。
> `relative_to_ls: true` 时，起点角度也是以左摇杆朝向为基准的。
>
> 判定是"累计角度**一进入**区间、并且**终点也对得上**就成功"，
> 所以转一整圈也会在路过时触发一次。转太多（超过 `max_angle`）则整段作废。

### `type: "sequence"` 的参数

| 参数 | 说明 |
|---|---|
| `steps` | 方向列表，每个元素的三种写法见下 |
| `tolerance_deg` | 每个方向的容错夹角，默认 35 |
| `enter_threshold` | 推过这个幅度才算一次有效点拨，默认 0.65 |
| `release_threshold` | 回落到这个幅度以下才算"松手"，默认 0.35 |
| `min_duration_ms` | 整个序列至少要花这么久，**太快直接作废**（默认 250） |
| `max_duration_ms` | 整个序列必须在多久内完成（默认 600，**必须大于各步 `hold_ms` 之和**） |
| `idle_timeout_ms` | 两步之间停顿超过这么久就清空进度（默认 250） |
| `require_neutral_between_steps` | 两步之间是否要求摇杆回中（默认 `true`，即真正的"点拨"） |
| `release_hold_ms` | 触发后要连续松开摇杆多久才重新武装，默认 150；防止按住不放连震 |

`steps` 里每个元素的三种写法：

| 写法 | 含义 |
|---|---|
| `"forward"` | 单一方向，点拨一下即可 |
| `["left", "right"]` | 这几个方向里**任一**都算 |
| `{"direction": [...], "hold_ms": 500}` | 方向对了还要**连续保持** 500ms 才算数 |

方向可以写名称（`forward`/`up`、`back`/`down`、`left`、`right`、`upright` 等），
也可以直接写角度数字（`0` / `90` / `180` / `270`）。

## 十、这台设备（飞智八爪鱼 4）的实测记录

在你这台机器上实测到的关键事实，省得以后重新踩：

- 手柄当前是 **XInput 模式**，系统里报告为 `Xbox One S Controller`
  （GUID `030044f05e040000e002000000007200`），6 轴 / 16 键 / 1 方向帽。
- 真实轴布局是 **左摇杆 = 轴 0/1，右摇杆 = 轴 2/3，LT = 轴 4，RT = 轴 5**，
  且**扳机静止值是 -1.0**（不是 0），推到底才是 +1.0。
  注意这跟 SDL XInput 驱动常见的 `0/1/4/5` 顺序**不一样**，所以代码里没有写死索引，
  而是向 SDL 的 GameController 映射表查询。
- **震动**：`pygame.joystick.Joystick.rumble()` 返回 `True`，可用；
  而 `pygame._sdl2.controller.Controller.rumble()` 在同一台设备上返回 `False`。
  所以震动主路径是前者。
- 250Hz 主循环实测稳定在 250Hz、0 次调度落后。

### 关于震动的一个坑（第一版踩过）

第一版把震动放在后台线程里播放，结果**触发时有时无、经常不震**。原因是
**SDL 的 joystick 子系统要求所有调用都发生在初始化它的那个线程上**：
主循环每秒 250 次 `pygame.event.pump()`，后台线程同时去调 `SDL_JoystickRumble`，
两者撞车，调用就被丢掉了。

现在震动改由**主循环每帧驱动**（`RumbleEngine.update()`），所有 SDL 调用都在同一线程里，
问题消失。仍然是非阻塞的——每帧只是比较一下时间戳，不做任何 `sleep`。
250Hz 意味着 4ms 的开关分辨率，对 50~200ms 的震动来说完全够用。

另外，第一版的震动参数是 `low: 0.0` + 55~70ms，这两个都偏保守：大马达全程没工作，
而 55ms 又不够马达转起来，所以即使震动真的下发了也很难感觉到。现已调整。

### 关于震动时长不规律的坑（第二版踩过）

第二版的震动引擎带一个队列：每次触发把"一串脉冲"推进队列，主循环一帧一帧地
往下播。问题是**几次挨得近的触发会被串成一串背靠背播放**，表现出来就是
"有时候震得正常，有时候特别短，有时候特别长、甚至一直在震"。

现在改成了**单脉冲状态机**：一次触发只下发一次震动，并记下截止时间，
到点必停；上一次没结束就来的新触发直接丢弃。再配合识别端的手势锁
（触发后必须回中 `gesture_release_ms` 才解锁）和每个动作的冷却，
震感就完全一致了——**所有动作都是低频 0.8、120ms，一次一下**。

## 十一、故障排查

**手柄识别不到**
用 `--list` 看。

- Windows：FIFA 本身需要 XInput，所以手柄最好切到 XInput 模式；换一个 USB 口试试。
- macOS：「系统设置 → 隐私与安全性 → 输入监控」里允许终端 / App；
  先用系统的「游戏控制器」面板确认系统本身能看到手柄。
- 有线连接通常比蓝牙更容易驱动震动。

窗口模式下如果手柄是后来才插上的，会自动重试；也可以按 `R` 手动重试。

**油炸丸子 La Croqueta 识别不到**
三个条件缺一不可：按住左摇杆给出朝向、按住 L1（LB）、右摇杆相对朝向偏 ±90°
（窗口 80°~100°），并保持到 350ms。窗口左侧的动作卡片会实时显示卡在哪一步：

- `方向对了，要按住 L1` —— 方向推对了，但 L1 没按（或没被识别）。
- `方向不对：当前 0°，要 右/左` —— L1 按住了，但相对角不在 80°~100°。
- `保持 右/左 210/350ms` —— 正在计时；松手太早会给出"保持不够"。

方向是**相对左摇杆**算的：先推左摇杆决定跑动方向，右摇杆再往那个方向的
正左/正右各偏 90°。左摇杆回中时没有方向基准，所有相对朝向的动作都不成立。
如果配置里写成 `relative_to_ls: false`，跑动方向一变就对不上，
表现出来就是"怎么推都识别不到"。

如果明明按着 L1 却一直提示"要按住 L1"，说明这个键没被识别到：
跑 `uv run main.py --debug`，按下 L1，看实时行里的 `键[...]` 有没有 `LB`。
没有的话在配置的 `input.axis_layout` 里重新映射按键（`L1` 的规范名是 `LB`）。

**还是识别不到？看诊断日志**
窗口版会自动把证据写到 `%APPDATA%\FifaSkillTrainer	rainer.log`
（macOS：`~/Library/Application Support/FifaSkillTrainer/trainer.log`）。
每次启动会记下加载的配置文件、它的修改时间、手柄按键/轴映射和每个动作的实际参数；
之后每次按键变化、右摇杆推下/松手、每 45ms 的角度/幅度/原始坐标/各识别器状态
都会记进去。做几次动作后打开日志，基本能直接看出是 L1 没被识别、方向不对、
还是保持时间不够。也可以在窗口里按 `C` 打开配置文件夹，日志就在旁边。

**窗口打不开 / 双击没反应**
先跑 `uv run app.py --demo`。演示模式不需要手柄，能把窗口问题单独隔离出来。
如果是打包版，用命令行运行 exe 看有没有报错（`--windowed` 会把 stderr 隐藏）。
配置写坏时窗口不会崩溃，会显示具体哪一行错了，按 `R` 重新加载。

**震动不生效 / 感觉很微弱**
先跑 `--selftest`，它会逐个试后端并告诉你哪个能用，然后依次用不同强度
（只有低频 / 只有高频 / 两个一起）和不同时长（60 / 120 / 200ms）各震一下，
让你直接挑出感觉得到的组合。`auto` 的后端顺序是：
`pygame` → `SDL2` → `XInput-Python` → `XInput ctypes`（后两个只在 Windows 上尝试）。

如果自检能震、但实际搓招时不震，看程序退出时打印的那行统计：

```
震动 12 次，⚠ 后端报错 3 次（后端返回失败（设备可能不支持该震动方式））
```

有"后端报错"说明震动下发了但被硬件/驱动拒绝；没有报错却感觉不到，
那就是强度和时长的问题，按上面第五节的"震感怎么调"调整。

如果所有后端都失败，可以装可选的 XInput 包再试（仅 Windows）：

```powershell
uv sync --extra xinput
```

也可以在配置里强制指定后端：`"rumble": { "backend": "xinput" }`。

**摇杆上下（或左右）反了**
窗口右下角的圆点应该和拇指同方向；`--debug` 里右摇杆上推应显示 `0.0°`。
如果相反，在 `skills_config.json` 里加：

```json
"input": { "invert": { "rs_y": true } }
```

只翻那一根轴，不用动轴号。详见第六节的「摇杆方向反了怎么办」。

**角度/按键对不上**
跑 `--debug`，推摇杆看角度、按键看编号。
如果布局识别错了，把 `--debug` 里看到的实际轴号填进 `skills_config.json`：

```json
"input": {
  "axis_layout": {
    "ls_x": 0, "ls_y": 1,
    "rs_x": 2, "rs_y": 3,
    "lt_axis": 4, "rt_axis": 5,
    "trigger_rest": -1.0,
    "buttons": { "A": 0, "B": 1, "X": 2, "Y": 3, "LB": 4, "RB": 5 }
  }
}
```

**老是误触发 / 触发不了**
先用 `--debug --trace` 看识别器实时进度，再调对应的阈值：
- 触发不了 → 放宽 `min_angle`~`max_angle` 区间、放宽 `max_duration_ms`、
  调低 `enter_threshold`、放宽 `start_tolerance` / `end_tolerance`
- 误触发 → 收窄角度区间、调高 `enter_threshold`、加 `direction` 方向约束、
  收紧 `start_angle` / `end_angle`
- 搓得很快但没反应 → 看 `min_duration_ms`，可能被判成"太快"作废了
- 两个动作老是串在一起 → 调小 `idle_timeout_ms`，或调大全局的 `input.idle_reset_ms`

**两个动作被认成一个 / 停顿之后还在接着算**
识别器只在"摇杆真的在动"的时候推进。停住不动超过 `idle_timeout_ms`（默认 180~300ms，
每个动作不同）或全局 `input.idle_reset_ms`（默认 250ms，右摇杆归中才算），
未完成的进度就会被清掉。如果你搓招本来就慢，可以适当调大这两个值；
如果老是被上一段的尾巴污染，就调小。

**配置文件写错了**
程序启动时会直接报错并指出是哪个动作的哪个字段，JSON 语法错误还会给出行号列号。
注意 JSON **不支持 `//` 注释**，最后一项后面也不能多写逗号。
