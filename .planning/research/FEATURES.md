# Feature Research

**Domain:** 手机架在手边 + 外接真手柄的搓招 / 手势肌肉记忆训练器（无游戏联动、纯本地）
**Researched:** 2026-11-04
**Confidence:** MEDIUM

> 研究口径：以 8 类相邻产品（打架游戏指令训练器、FPS 瞄准训练器、打字训练器、乐器练习 App、练习计时器、手柄检测/校准 App、节奏游戏、现有桌面版）的实际功能为样本，用运动学习文献校验"哪些机制真的有证据"。凡是文献与产品惯例冲突的地方，本文按文献走并显式标注。

---

## 一句话结论

这个产品的功能重心不是"更多动作"，而是**让一次尝试的结果在 1 秒内被看懂，并且整场练习不需要碰屏幕**。桌面版已经解决了"判得准"，移动版要解决的是"看得懂 + 不用手"。

判定一致性是底线（不是特性），**免触摸循环 + 量化反馈**才是移动版真正的产品价值。

---

## 会话形态建议（先定骨架，再谈特性）

现有桌面版是"10 个一组"。这个粒度是对的，移动版应把它明确成四级结构：

| 层级 | 内容 | 时长 | 说明 |
|------|------|------|------|
| 尝试 Attempt | 一次搓招 | < 2 s | 判定单元，产生一条结果 |
| 组 Set | 同一动作 × 10 次 | 40–60 s | 现有桌面版已有；这是"进步"的可感知单位 |
| 回合 Round | 同一动作 × 3 组 | ~3 min | 组间 15–20 s 自然间隔，不需要倒计时器 |
| 会话 Session | 1 个弱项动作 × 3 组 + 1–2 个其他动作 × 1 组 | 5–15 min | 沙发场景的真实上限 |

**关键判断：**

- **不要做"课程 / 章节 / 关卡"体系。** 只有 5 个动作，做成课程会立刻显得内容贫乏；而且用户是来练肌肉记忆的，不是来通关的。
- **不要做组间休息倒计时。** 10 次一组只有 40–60 秒，休息器是多余的仪式。真要防疲劳，在会话层做"已练 10 分钟，要不要收"的软提示即可（P3）。
- **会话长度可选（5 / 10 / 20 分钟）是廉价且有效的差异化**：Yousician 用 10/20/30 分钟三档做主导航，用户不必自己想"今天练什么"。复杂度低，但依赖"弱项统计"才能自动组课。
- **默认入口 = 直接开练，不是首页。** 冷启动若手柄已连，直接进上次的动作并处于待触发状态。"打开就能练"比任何仪表盘都重要。

## Feature Landscape

### 表内必备 (Table Stakes)

缺了就不像成品，用户不会给分，但会因此流失。

| 特性 | 类别 | 为什么必须有 | 复杂度 | 依赖 |
|------|------|--------------|--------|------|
| 判定与桌面版逐项一致（5 个动作） | 判定 | 这是产品定义本身；230 项检查是验收规格书 | 高 | 配置单一真源 + 三类检测器移植 |
| 手柄连接 + "按任意键唤醒"引导 | 接入 | Android 蓝牙手柄在收到第一次输入前不会出现在输入列表里，B 站/论坛大量"连不上"其实都是没按键 | 低 | 无（一切的前置） |
| 断连检测 + 自动重连 | 接入 | 沙发场景蓝牙必掉；掉线时正在做的动作不能算失败 | 中 | 手柄连接 |
| 摇杆校准：中点 + 满量程 | 接入 | 弧线阈值按归一化半径算；磨损摇杆推不到 1.0 会把硬件问题判成"你转得不够" | 中 | 手柄连接 |
| 待触发 / 冷却状态可见 | 反馈 | 配置里有 `release_hold_ms`、`cooldown_ms`、`idle_timeout_ms`；用户必须知道"现在这一下算不算" | 低 | 检测器状态机 |
| 免触摸自动循环（做完自动进下一次） | 会话 | 手在手柄上、手机在架子上；每做一次都要点屏幕 = 产品不可用 | 低 | 结果停留时长 + 检测器重新武装 |
| 失败原因一行说清 | 反馈 | 核心价值；桌面版已有 `FAILURE_LABELS` + `_ADVICE` 两套文案可直接搬 | 低 | 检测器错误码 |
| 实测值 vs 目标区间（时序条） | 反馈 | 只说"780 ms"没有意义；给出 600–750 ms 绿带 + 本次落点，一眼定位偏差方向 | 中 | **检测器需输出结构化度量，而不只是错误码** |
| 一组 10 次 + 组内进度点 | 会话 | 训练的基本单位，桌面版已有 | 低 | 结果记录 |
| 最近尝试列表（可滚动） | 会话 | 复盘用；桌面版保留 50 条 | 低 | 结果记录 |
| 暂停 / 继续（且必须重置检测器） | 会话 | 中途接电话、拿水。**绝对时间轴在恢复时会算出巨大 elapsed → 误判"太慢"**，这是移动端最容易被忽略的判定污染源 | 低（但风险高） | 引擎会话重置 |
| 屏幕常亮 | QoL | 手不碰屏幕，系统 30 秒就黑屏 | 低 | 无 |
| 横屏锁定 + 架子距离可读的字号 | QoL | 手机在 40–70 cm 外，正文必须 ≥ 20 sp；竖屏排版留到之后 | 中 | 无 |
| 手柄布局标识切换（Xbox / PlayStation） | 上手 | 用户按 ✕/□ 找键，标签错了就永远找不到。**Android 上 `Input.get_joy_info()` 返回空、DualSense 被系统改写映射，不能自动识别**，只能手动选 + 按键确认 | 低 | 无 |
| 震动尽力而为 + 震动自检 | 反馈 | Godot 安卓端手柄震动按型号差异极大（Xbox 有线常可用，DualSense 常不可用）；先让用户按一下测试，再决定是否指望它 | 低 | 手柄连接 |
| 音效开关（成功/失败） | 反馈 | 视觉是主路径，但音效让用户不必一直盯着屏幕 | 低 | 无 |
| 本地持久化（重开还在） | 数据 | "今天练了多少"必须跨启动存在 | 低 | 无 |

### 差异化 (Differentiators)

不是必须有，但决定"为什么用这个而不是开着练习模式瞎搓"。

| 特性 | 价值 | 复杂度 | 依赖 |
|------|------|--------|------|
| **本次轨迹回放（0.5×，失败点高亮）** | 把"我错在哪"从一句话变成一段可看的动作。运动学习里"自我控制反馈"（self-controlled feedback）比强灌反馈更能迁移 | 中高 | 采样环形缓冲 + 轨迹录制 |
| **示范一次（参考轨迹，按需播放）** | 用配置参数合成理想轨迹（弧的起止角 + 扫过角；序列的方向 + 保持；点按的时间轴），按一下播一遍，播完隐藏。Frame Dojo 的 "Show me" 就是这个 | 中高 | 参考轨迹生成器 + 轨迹回放 |
| **序列动作的逐步拆解** | 总时长 620 ms 达标，但第 2 步慢了 90 ms —— 只看总时长永远修不好。打架游戏训练器的标准做法是逐步 frame delta | 中 | 检测器输出每步耗时 |
| **弱项加权 / 聚焦最差动作** | keybr 的 focus key、MotionInputs 的 spaced-repetition focus 都靠这个把"练 5 个"变成"练该练的那个" | 低中 | 每动作统计 |
| **混合练习模式（交错练习）** | 随机/交错练习对留存与迁移优于分块练习（证据较稳），但**练的时候感觉更差**——所以两种模式都要给，不能只给交错 | 低 | 多动作调度 |
| **每动作准确率趋势** | 桌面版只有 50 条流水，没有趋势。"上周 6/10，这周 8/10"才是进步感 | 低中 | 持久化 + 聚合 |
| **干净连击 / 最佳连击** | 比准确率更能反映稳定性；Ironfist Insights 的 `streak (best)` 就是这个 | 低 | 结果记录 |
| **手柄当遥控器** | Start 暂停、十字键换动作、Y 回放、LB 看示范。沙发上不用摸手机就能控制一切 | 低 | **必须避开 `required_button` 已占用的键（X 已是部分动作的按键）** |
| **会话小结** | 结束时给"今天 5 个动作 50 次，马赛回旋 8/10，最差踩单车 4/10，下次先练它" | 低中 | 会话聚合 |
| **节奏音（序列动作的节拍点击）** | Ironfist 的 "Hear the rhythm"：把时序目标变成可听的节拍，比看条更快形成节奏感 | 中 | 音频 + 时序目标 |
| 掌握等级（每动作铜/银/金） | 具体规则建议：连续 1 组 ≥8/10 = 铜，2 组 = 银，3 组 = 金。注意别做成"必须刷到金才能继续练" | 低中 | 弱项统计 + 连击 |
| 多手柄档案（校准值按手柄存） | 换了手柄判定不该变；手柄检测类 App 全都做 per-controller profile | 中 | 校准 + 设备标识（Android 上难） |

### 反特性 (Anti-Features)

看着合理、实际会毁掉这个用例。列出来是为了在 roadmap 阶段直接拒绝。

| 反特性 | 为什么会被想要 | 为什么有害 | 替代做法 |
|--------|----------------|------------|----------|
| 账号 / 云同步 | "换手机不丢数据" | 打开就要登录，破坏"拿起就练"；还要服务端与隐私合规；本项目已明确 out of scope | 本地存储 + 手动导出 JSON |
| 排行榜 / 全球排名 | "有竞争才有动力" | 只有 5 个本地动作，样本量极小；不同手柄、采样率、阈值让分数不可比；还要后端 | 只和自己上周比 |
| 社交 feed / 分享短视频 | "增长" | 与练肌肉记忆无关；要处理上传、隐私、审核 | 本地截图卡片（可选导出） |
| 广告 | 变现 | 一组只有 40–60 秒，插屏广告直接打断节奏，且 APK 侧载没有变现诉求 | 不做 |
| 强制教程 | "新手需要引导" | 老用户每次都要跳过；沙发场景最烦多一步 | 一次性 3 步可跳过 onboarding + 随时可开的 "?" 面板 |
| 虚拟摇杆 / 触屏搓招 | "没手柄也能玩" | 触屏搓招的肌肉记忆无法迁移到真手柄；PROJECT.md 已明确排除 | 无手柄时只展示连接引导 |
| 自动收紧判定阈值（难度爬升） | "让高手也有挑战" | 历史数据立刻不可比；用户不知道自己在和什么比 | 手动难度档（宽/标准/严），**档位写进每条记录** |
| 单一总分 / 综合评分 | "一个数字好传播" | 掩盖"哪个动作弱"，而这正是用户最需要的信息 | 分动作准确率 + 弱项高亮 |
| 常驻参考轨迹（一直显示的 ghost） | "有对照才练得准" | Guidance hypothesis：持续视觉引导会让练习表现变好、留存变差，撤掉就不会做 | 按需播一次，播完隐藏 |
| 失败时自动慢放教学 + 弹窗 | "更贴心" | 打断节奏，且把训练变成看视频 | 失败只留一行原因，回放由用户按需触发 |
| 自动识别手柄型号并静默改映射 | "省一步" | Android 上拿不到 raw name / vendor id，DualSense 还会被系统改写按钮布局，猜错比不猜更糟 | 手动选布局 + 按键确认页（按 A 显示 A） |
| XP / 金币 / 皮肤 / 每日签到 | "提升留存" | 把训练工具变成运营产品，稀释核心；本项目没有变现目标 | 只保留"练了几次/几天"这类事实性统计 |
| 严格每日连续打卡（断一天清零） | "streak 有效" | 制造焦虑，且一次断掉就彻底放弃；Simply Piano 用**周**为单位并给"冻结"就是为此 | 周 streak + 冻结，或只显示"本周练了 3 天" |
| 悬浮窗覆盖游戏 / 注入输入 | "直接在游戏里练" | Android/iOS 均无法合法注入手柄输入；悬浮窗权限还会带来一堆适配问题 | 纯本地训练器，定位为场外练习 |

## 关键设计判断（按提问的五个维度）

### 1. 会话形态

- **单位要小、循环要自动。** 参照练习计时器类产品（Timglas、Dugout Edge、Fretlist Play Mode）的共识：`auto-advance` + `screen stays awake` + `no account` 是"手机架在架子上、双手占用"场景的三件套。缺 auto-advance 的产品在这个场景里等于不可用。
- **不要照搬 Aim Lab 的 45 分钟课程结构。** 那是 PC 上前置热身场景；本项目是沙发上的碎片练习。20–30 分钟是上限不是目标。
- **自由练习 + 组制并存**：默认"10 次一组"，另给"不限次数"（只连续判、不计数）。自由练习是低成本高使用率的功能。

### 2. 反馈设计

分三层，时间尺度不同：

| 层 | 时机 | 内容 | 要点 |
|----|------|------|------|
| L1 即时 | < 100 ms | 圆环变色 + 成功音 / 震动 | 必须在结果算出来的同一帧；不要等动画 |
| L2 单次结果 | 停留 1.5–2.5 s | 大字号原因 + 实测条 + 一行建议 | 原因写在**用户视线已经在的地方**（摇杆环旁），不要放角落 |
| L3 组结束 | 组末 | 本组 x/10 + 最差的一次 + 该动作趋势 | 只在这一层做"复盘"，不打断单次节奏 |

- **失败原因的写法：现象 + 差多少 + 怎么改。** 现有 `_ADVICE` 只有"怎么改"，移动版应补上量化："慢了 90 ms —— 起手太早，等摇杆到 3 点方向再转"。
- **成功震、失败不震。** 桌面版就是这个策略，是对的：失败震动既惩罚又语义模糊（用户分不清是"失败"还是"没识别到"），而失败已经有视觉主路径。
- **颜色不能是唯一编码。** 红/绿 + 图标 + 文字三重编码，成本极低。
- **音效默认开、可关；节奏音默认关、按动作开。** 节奏音只对序列类动作有意义。
- **轨迹回放是"最高性价比的差异化"**，因为移动端最缺的正是"我看不见自己做了什么"。实现上只需要一次尝试的采样环形缓冲，不需要录像。

### 3. 进阶机制

这里必须跟文献对齐，否则会做出一个"看起来很科学但没证据"的系统：

- **不要做 Anki/SM-2 式的间隔重复排程。** 2026 年 *Scientific Reports* 的研究显示，间隔练习对动作序列学习的**学习效果**几乎没有优势（只有训练期内的暂时表现优势）；把记忆类 SR 模型套到动作技能上没有依据。
- **有证据的杠杆是"交错"而不是"间隔"。** 随机/交错练习在留存与迁移上优于分块练习（多篇一致），代价是练的时候感觉更差。所以：**给两种模式，并解释差异**，让用户自己选。
- **"弱项加权"是工程启发式，不是科学结论。** keybr 的 focus key 有效是因为它把练习时间重新分配，不是因为它算出了记忆强度。文案上不要宣称"科学算法"。
- **具体建议的统计口径：**
  - 每动作：总次数、成功数、准确率（最近 50 次）、最佳干净连击、时长中位数、上次练习日期
  - 弱项 = 准确率最低且样本 ≥ 20 次（避免"第一次就 0/1"被当成弱项）
  - 趋势 = 最近 5 组准确率的 sparkline，不做曲线拟合
- **掌握等级只在有足够样本时解锁**，否则会出现"第一次就拿了铜牌"的荒谬感。

### 4. 上手与校准

- **冷启动直达练习**，不设首页。手柄已连 → 直接进上次动作的待触发状态。
- **3 步 onboarding，可整段跳过**：
  1. 配对引导（按型号分支：Xbox 配对键长按至闪；DualSense 关机后 PS + Create 长按）——这是全网"连不上"问题的真正答案，值得做成图文。
  2. 校准：摇杆推满一圈，记录中点偏移与满量程。
  3. 按键确认：屏幕显示 "A"，用户按 A，确认映射。
- **布局选择必须手动**（Xbox / PlayStation 图标），原因见反特性表：Android 上拿不到可靠的设备标识。
- **校准值要落盘并按手柄存**，即使 v1 只存一份，数据结构也要留 `profile_id` 字段，否则 v2 迁移要返工。
- **左摇杆朝向基准要显式化。** `relative_to_ls=true` 的动作以左摇杆朝向为 0°，而移动端没有"球员朝向"这个语境。必须在屏幕上画出左摇杆方向 + 一句"推住左摇杆定朝向"。这是移动版独有的理解成本，不能靠用户猜。

### 5. Quality-of-Life

| 场景 | 应有行为 | 复杂度 |
|------|----------|--------|
| 蓝牙掉线 | 顶部横幅 + 冻结计时；当前这次尝试**丢弃不计失败**；重连后回到待触发 | 中 |
| 切后台 / 锁屏 | 立即暂停并重置检测器状态；回来显示"准备…3 2 1"再开 | 低 |
| 暂停 | 手柄 Start 或点屏幕；恢复时 3 秒倒计时，避免手还在口袋里就开始判 | 低 |
| 屏幕常亮 | 前台常亮，退到后台自动放开 | 低 |
| 旋转 | v1 锁横屏；竖屏排版 v2 | 低 |
| 夜间 / 昏暗 | 深色低亮主题（沙发、关灯场景刚需） | 低 |
| 电量 | 无网络、无后台服务；不做"省电模式"这类复杂度 | 低 |
| 误触 | 判定区域不吃触摸；按钮 ≥ 48 dp | 低 |

## Feature Dependencies

```
[手柄连接 / 重连]
    └──requires──> [摇杆校准]
                       └──requires──> [检测器归一化] ──requires──> [判定一致性]

[检测器状态机] ──requires──> [待触发指示]
[检测器结构化度量] ──requires──> [实测 vs 目标区间] ──enhances──> [逐步拆解]

[轨迹录制 / 环形缓冲] ──requires──> [本次回放] ──enhances──> [失败点高亮]
        └──requires──> [参考轨迹叠加] ──requires──> [示范一次]

[结果记录] ──requires──> [组内进度] ──requires──> [组末小结]
      └──requires──> [本地持久化] ──requires──> [每动作统计]
                                          ├──requires──> [趋势]
                                          ├──requires──> [弱项加权] ──requires──> [混合练习 / 自动组课]
                                          └──requires──> [掌握等级]

[会话聚合] ──requires──> [会话小结]

[暂停 / 恢复] ──conflicts──> [绝对时间轴判定]   （必须显式重置，否则误判"太慢"）
[手柄当遥控器] ──conflicts──> [required_button 占用同一按键的动作]
[自动收紧阈值] ──conflicts──> [趋势可比性 / 历史数据]
[常驻 ghost] ──conflicts──> [无引导下的独立完成能力]
```

### Dependency Notes

- **检测器结构化度量是隐藏的关键路径。** 现有桌面版只吐 `code` + `message` + `elapsed_ms`；"实测 vs 目标区间""逐步拆解""失败点高亮"全都要求检测器额外输出 `measured{}`（起止角、扫过角、每步耗时、保持时长）。这一层要在移植检测器时就留出接口，否则后面所有反馈特性都要返工。
- **校准必须先于判定。** 归一化半径直接进入弧线阈值；没有校准，同一个动作在不同手柄上判定不同。
- **轨迹录制是"回放"和"示范"的共同底座。** 先做录制与回放，参考轨迹生成器可以后做。
- **弱项加权依赖统计，统计依赖持久化。** 因此 v1 即使只存最朴素的计数，也要把 schema 定好。
- **手柄当遥控器与动作按键冲突。** 现有动作里 X 是按键（油炸丸子、绿色搓射）。UI 快捷键只能用 Start / Select / 十字键 / 肩键里未被 `required_button` 占用的部分，并在加载配置后动态校验。
- **暂停与绝对时间轴冲突。** 桌面引擎用绝对时间轴追帧，这是正确的；但移动版生命周期会让 dt 变成几十秒。必须把"前台时间"与"墙钟时间"分开。

## MVP Definition

### Launch With (v1) — 标准是"能连续每天用"

验收测试（建议直接写进 UAT）：**不看说明书，连续做 30 次尝试，全程不碰屏幕，能说出每次错在哪一类。**

- [ ] 判定与桌面版一致（5 个动作，230 项检查作为验收）—— 产品定义
- [ ] 手柄连接 + 按任意键唤醒的图文引导 —— 否则第一步就卡住
- [ ] 断连检测 + 自动重连（掉线不算失败）—— 沙发场景必需
- [ ] 摇杆校准（中点 + 满量程，单档案，schema 预留 profile_id）
- [ ] 待触发 / 冷却状态可见
- [ ] 免触摸循环：10 次一组，结果停留后自动进入下一次
- [ ] 失败原因一行（大字号）+ 实测 vs 目标区间时序条
- [ ] 组内进度点 + 最近尝试列表
- [ ] 暂停 / 恢复（含检测器重置 + 3 秒倒计时）
- [ ] 屏幕常亮 + 横屏锁定 + 架子距离字号
- [ ] 布局切换（Xbox / PlayStation）+ 按键确认页
- [ ] 震动尽力而为 + 震动自检 + 开关
- [ ] 音效开关
- [ ] 本地持久化（每动作尝试数 / 成功数 / 最近记录）
- [ ] 冷启动直达上次的动作

### Add After Validation (v1.x)

触发条件：v1 已经能每天用，且用户开始抱怨"看不清自己做了什么"或"不知道该练哪个"。

- [ ] 本次轨迹回放（0.5×，失败点高亮）—— 用户开始问"我到底哪里错了"时
- [ ] 示范一次（参考轨迹按需播放）—— 用户开始问"正确的是什么样"时
- [ ] 序列动作逐步拆解 —— 出现"总时长对了但就是不成"的反馈时
- [ ] 每动作准确率趋势 + 弱项高亮 —— 记录积累到 ~200 次之后才有意义
- [ ] 弱项加权 / 混合练习模式 —— 趋势有了才谈得上"该练哪个"
- [ ] 组末 / 会话小结
- [ ] 干净连击 / 最佳连击
- [ ] 手柄当遥控器（Start 暂停、十字键换动作、Y 回放）
- [ ] 节奏音（仅序列类动作）
- [ ] 会话长度选择（5 / 10 / 20 分钟自动组课）

### Future Consideration (v2+)

- [ ] 掌握等级（铜/银/金）—— 需要样本量与防刷设计，做早了会显得随意
- [ ] 多手柄档案对比 —— 需要可靠的设备标识，Android 上成本高
- [ ] 统计导出 / 导入 —— 没有跨设备需求前不做
- [ ] 竖屏 / 平板排版 —— 横屏能覆盖绝大多数支架
- [ ] 动作库扩充（> 5）—— 本项目首版明确不扩充
- [ ] 难度档（宽/标准/严）—— 会破坏历史可比性，必须和"档位写进记录"一起做

## Gaps to Address

- **摇杆采样率对判定稳定性的实测影响**：桌面 250 Hz，移动 60–125 Hz。特性上不新增，但"实测 vs 区间"这条 UI 依赖抖动数据；需要在真机上量一次 60/90/120 Hz 下的 elapsed 分布，再决定时序条要不要画 ±1σ 阴影。
- **震动能力矩阵**：Xbox 蓝牙 / Xbox 有线 / DualSense 蓝牙 / DualSense 有线 四种组合的真机结果未知。影响"震动自检"的文案与默认开关，需要真机验证（PROJECT.md 已列为约束）。
- **Android 上 DualSense 的按钮映射偏移**：有产品专门做 "PS Mode (Type 2)" 来处理系统改写。需要实测确认 Godot 里读到的按钮索引与图标是否能对上，否则"按键确认页"要从"确认"升级为"重映射"。
- **左摇杆朝向基准在移动端的必要性**：如果用户只是在场外练形状，`relative_to_ls=false` 更直观；如果要迁移到游戏，必须 LS 相对。这是个产品取舍，建议 v1 保留两种并默认 LS 相对 + 屏幕画出方向，等真实使用反馈再定。
- **"一次尝试"的判定窗口与 auto-advance 停留时长的配合**：停留太短看不清，太长破坏节奏。需要用真人在 1.2 / 1.8 / 2.5 s 三档上试。
- **是否需要一个"无判定纯自由搓"模式**：用户可能想先熟悉手柄手感。成本极低，但没有证据支持其必要性，留作观察项。
